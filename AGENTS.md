# OpenSkateMap cloud

The backend for OpenSkateMap: one Cloudflare Worker (Hono API) in front of PlanetScale Postgres with PostGIS
through Hyperdrive, R2 for photos and clips. The iOS app's client is generated from `apps/api/openapi.json`.

## Layout

- `apps/api` — the Worker. `cloudflare.config.ts` declares every binding (the `cf` CLI generates `Env` from it),
  `src/app.ts` assembles middleware and routes, `src/routes/*` one file per resource, `src/services/*` the queries
  and writes behind them (scripts reuse these too), `src/lib/*` the envelope, errors, results, schemas and router
  factory. `scripts/*` are admin and dev tools run with bun.
- `apps/web` — openskatemap.app: the landing page (`landing/`, its own Astro package `@openskatemap/landing`; `scripts/build-pages.ts` builds it first, `buildPages` writes it as `/` with its share tags and `/assets/*` is copied beside; `/` carries Astro's `security.csp` `<meta>` policy, which hashes its inlined stylesheet and scripts, and its header adds only `frame-ancestors`; every other page inlines `pageStylesheet` and its policy allows only that stylesheet's hash (a test keeps the hash in step); never `unsafe-inline`; avatars are rasterized to WebP named by content hash, because WebKit applies the page policy to SVG style attributes; `buildPages` also writes `robots.txt` (Content Signals, AI crawlers), `llms.txt` and the home page's twin `index.md`, and `_headers` sends `Content-Signal` and `Link` to both; the spot and collection fallbacks are noindex), the legal texts the app links to (`/terms`, `/privacy`, plus
  `/terms.md`, `/privacy.md` for agents) and `/support` (the App Store's support URL) as static assets, and a Worker (`src/index.ts`) for `/spots/*`,
  `/cards/spots/*` and the pages with a Markdown twin (`markdownTwins`, which answer `Accept: text/markdown` with it; `runWorkerFirst`). `content/*.md` is the only source:
  `scripts/build-pages.ts` renders it through `site/pages.ts` into `.pages/` on `bun run build`, `dev` and `deploy`,
  which then hand `.pages` to Wrangler (`wrangler.jsonc`). The support address is `site.contact` in `site/site.ts`; until it's set the texts say it's coming.
  Every page shares as a large card (`site/cards.ts`): a 1800 × 945 JPEG (1.91:1) in the site's light style, rendered
  by `scripts/share-images.ts` and committed in `site/share/`: the home page's from the landing itself; the legal
  pages', support's and the spot and collection fallbacks' (`shareCards`) in one layout (icon and wordmark, the title,
  its note, two of the landing's hero pins). `buildPages` writes each to `/cards/<name>.<hash>.jpg` (cached immutable),
  named by `og:image` / `twitter:card` tags.
- **Spot links** (`/spots/<id>`): the Worker asks the API for the spot's public card (`GET /v1/spots/{id}/card`, over
  the `API` service binding) and renders the page with that spot's tags; its card image
  (`/cards/spots/<id>/<version>-<design>.jpg`) is composed on request by the Images binding (`src/spot-card.ts`):
  a white base with the tile's shadow and the wordmark, the cover from `images.openskatemap.app` cropped square to the
  tile (straight: Images rotates only by quarter turns) or, without a cover, the kind's empty tile (its colour at 16%
  over white with a map pin), the frame that rounds its corners and draws the white border, the "See the spot" pill,
  then the name and "Kind · City" placed from the fonts' metrics (`site/spot-card-layout.ts`, `site/font-metrics.ts`
  generated by `scripts/font-metrics.ts`). The base, empty tiles, frame and pill come from `scripts/share-images.ts` (`site/share/spot-card/`);
  the text is Inter Display Bold and Regular (rsms/inter v4.1, unmodified, `apps/web/fonts`, SIL OFL 1.1), served at
  `/fonts/*` because Images loads fonts by URL, from the request's own origin so a preview draws with its own fonts.
  A change to the card's look bumps `spotCardDesign`, which is in every card URL. Pages are cached 5 minutes and cards a day (Cache API; the URL already carries the version and design). A spot the
  API doesn't know (removed, unknown, or the API unreachable) gets the generic `spot.html`. The Worker does layout
  only; Images does the pixels (written when the account was on Workers Free; it's on Workers Paid since 2026-10-13).
- `apps/web/scripts/share-images.ts` — renders every share image from HTML in headless Chrome, then `sips` (so on a Mac, in the system font like the site): the home page's (`apps/web/site/share/home.jpg`, 1800 × 945: 1.5× keeps it under WhatsApp's ~300 KB preview limit) and the READMEs' header (`.github/assets/hero.jpg`; pass the iOS repo's path as an extra output) from the built landing page as one composition (the hero without its badges, notes placed clear of the spots), the other pages' cards (`site/share/<name>.jpg`) and the spot card's parts at 1× (`site/share/spot-card/`; a test checks their sizes against the layout). Run `bun run build` first (it needs only the landing's `.site`), then the script, and commit the images that changed.
- `packages/db` — Drizzle schema, SQL migrations, the connection helper, the migration runner.
- `docker-compose.yml` — local Postgres 18 + PostGIS 3.6 on port 54330 (project name `openskatemap`).

## Rules that hold everywhere

- **Deny by default.** An operation is either in `src/lib/public-operations.ts` (with a reason, declared with
  `publicRoute()`, which spends the caller's address budget) or is declared with
  `authedRoute()` (`src/lib/routes.ts`), which adds `bearerAuth` to the spec and the middleware that enforces it:
  `requireBearer` (401 before any database work), `withDatabase`, `withAuth`, `requireUser` (session + ban check),
  then the route's own middleware such as `requireRole("editor")`, passed as `authedRoute(config, ...middleware)`. `test/contract.test.ts` calls every guarded
  operation without a token and fails the build unless it answers 401.
- **Auth** is Better Auth with native Sign in with Apple only (`src/auth/create-auth.ts`): the app sends Apple's
  identity token to `POST /v1/auth/apple`, verified against Apple's keys with our bundle ids as audience. Better
  Auth's HTTP routes are not mounted; the typed `/v1` routes call `auth.api` in-process. Roles: user / editor / admin
  (`src/auth/roles.ts`). When the app sends Apple's `authorizationCode`, the server trades it for Apple's refresh
  token and keeps it encrypted in `apple_token`, only so `DELETE /v1/me` can revoke it first (App Review requires
  that). Apple's server-to-server notices arrive at `POST /v1/auth/apple/notifications` (registered on the App ID
  com.ertembiyik.openskatemap → Sign in with Apple → Configure; `src/auth/apple-notifications.ts` verifies the JWT
  against Apple's keys, issuer and our bundle ids): `consent-revoked` and an Apple Account's deletion end every session
  created before the event and drop the stored Apple token (`applyAppleAccountEvent`), so a late or repeated notice
  never ends a newer sign-in. A deleted Apple Account also schedules ours for deletion 30 days later
  (`apple_account_deletion`, Ertem 2026-10-20), unless someone signed in since; signing in again cancels it quietly
  (`cancelAppleAccountDeletion`), and the daily housekeeping cron deletes accounts that are due as Delete Account does
  (`deleteDueAccounts`, then `eraseElsewhere` for the push subscriber and the analytics person). After `consent-revoked`
  the account stays. The app also checks the credential's state itself.
  The client secret is an ES256 JWT signed with the Sign in with Apple key (`src/auth/apple-tokens.ts`, team
  MD55Y22MQS, key M7GZGGC9Z8); without `APPLE_SIGN_IN_KEY` both steps are off. The auth schema is generated: `bunx auth generate --config src/auth/cli-config.ts --output
  ../../packages/db/src/schema/auth.ts` (in `apps/api`), then `bun run db:generate`.
- **Zod at every boundary**: params, query, body and responses are `@hono/zod-openapi` schemas, so the spec and
  the Swift client follow from them. Never hand-write a response type.
- **One envelope.** Success is `{ ok: true, data }`; failure is `{ ok: false, error }`, made only by `respondError`
  from an `ErrorCode`. `errorResponses` is spread into every route and must not be `as const`.
- **Errors are values.** Expected failures travel as neverthrow results (imported only through `src/lib/result.ts`);
  a service with none (a plain read) returns its value. A thrown exception is a bug and becomes `internal_error`.
  Where a body checks several results in turn (a transaction's), it's `safeTry(async function* (): Attempt<T, E> { … })`
  and `yield*`s each one; a route whose answer is the service's result is `reply(c, result)`.
- **Query numbers** use `queryNumber()` (`src/lib/query.ts`), not `z.coerce.number()`, which accepts `""` as 0 and
  shows up in the spec as an optional `number | null`.
- **Comments:** the code explains itself (names, types, small functions). A comment says only what the code can't:
  a platform quirk (Workers, Hyperdrive, Better Auth, Images, node-postgres), a security or privacy invariant, where a
  measured constant comes from, a non-obvious type contract or ordering rule. One line where it can be; never restate
  the code, narrate a change, say who decided it or when (that's git and this file), or name a reference app. Every
  larger change re-checks its own comments (Ertem, 2026-10-19; sweeps: 2026-10-14, 2026-10-19).
- **No private data in logs.** Log an error's name and database code (`src/lib/log.ts`), never messages,
  query parameters, emails or tokens.
- **Constraints live in the schema.** A CHECK over a schema's own constants (`review_event_action_known` from `REVIEW_ACTIONS`, the collection colours and kinds) is declared with `check()` and `quoted()` (`packages/db/src/schema/checks.ts`), so `db:generate` writes the change and its snapshot knows it; never hand-write one in a custom migration (drizzle-kit can't see it).
- **Two database roles.** The Worker connects as the restricted app role (`openskatemap_app`: read and write rows,
  own nothing); migrations run as the migration role. Migrations are additive: they run before new code deploys.
- **Request-sized timeouts on the app role** (`APP_ROLE_SETTINGS`, `packages/db/src/app-role.ts`): statements 5 s,
  lock waits 2 s, idle in a transaction 5 s, a transaction 10 s (PlanetScale's connection-resilience guidance). They
  are the role's own defaults, because Hyperdrive resets every pooled connection, so a `SET` never outlives its
  transaction; `db:migrate` applies them when `DATABASE_URL_APP` is set (a role may set its own; on PlanetScale the
  migration role can't). Work that needs longer opens a transaction, `set local transaction_timeout = 0` (a running
  transaction's timeout can only be turned off, never extended) and its own `statement_timeout`, as the spot-score
  refresh does. A timeout is a 503 `unavailable` logged as "Database timeout" with its Postgres code (`TIMEOUT_CODES`).
  Migrations wait at most 3 s for a lock, then fail and roll back rather than queue the API behind them. Never call
  out to the network inside a transaction.
- **One connection per unit of work** (`openDatabase`); Hyperdrive pools. Close it when the request is done. One
  connection runs one query at a time: await queries in turn, never `Promise.all` on the same `db`.

## Spots and sync

- **The version is the sync cursor.** Migration 0003's trigger gives every spot insert and update the next
  `spot_version_seq` value under a transaction-scoped advisory lock, so versions follow commit order and a client
  that has seen version N has seen everything at or below it (`e2e/spots.test.ts` proves the wait). Never set
  `version` or `city_id` yourself.
- **Never delete a spot.** Removing one is `status = 'removed'`; `GET /v1/sync/spots` sends it as a tombstone (except from cursor 0: a fresh install has nothing to delete). An admin takes a spot down (public or private) with `PUT /v1/spots/{spotId}/removal` and a reason (`SPOT_REMOVAL_REASONS`), stored on the spot (`removal_reason`, `removed_at`: set only by a takedown, so a spot an undone approval removed has none), with a `remove` review event the first time only; `DELETE /v1/spots/{spotId}/removal` restores it under a new version, with a `restore` event (`src/services/curation.ts`; the app's More → Delete Spot and its Undo, Ertem 2026-10-20). Submissions carry `removal`, so the rider's history keeps the row as removed with the reason, while profile stats leave it out (`isTakenDown`, `src/services/submissions.ts`).
  A photo insert, update or delete touches its spot, so the cover in the index row syncs too.
- **Cities**: a spot belongs to the smallest city whose area contains it (`spot_city_for()`, SQL). `saveCity()`
  re-files spots when an area changes.
- **Locations** use the `point` column type (`packages/db/src/schema/geo.ts`): it writes EWKT with SRID 4326 and
  reads hex EWKB. Drizzle's built-in `geometry` drops the SRID, which a 4326 column rejects. Distances in meters use
  `::geography` on both sides, which matches the expression index `spot_location_geography_gist`.
- **Light and heavy rows**: the sync index row is what the map needs (title, kind, condition, point, cover) plus
  what apps filter on offline (obstacles); everything else comes from `GET /v1/spots?ids=` for the spots on screen.
  The sync and the collections snapshot select the same `indexColumns` (`src/services/spots.ts`).

## Search

- **`GET /v1/spots/search`** (`searchSpots`, `src/services/spot-search.ts`) finds published public spots by name for
  the app's local search while its index is still syncing. Rows are the sync's `indexColumns`, so the app stores them
  like synced ones.
- **Names are compared in Latin letters.** `spot.search_text` is a stored generated column, `search_words(title)`
  (SQL, migration 0033): Cyrillic romanised (й as both i and y, ё as e), lowercase by the built-in `pg_c_utf8`
  whatever the database's collation, accents off (`unaccent`), anything but letters and digits a space. Queries go
  through `search_fold()`, the same rules. Latin because pg_trgm sees only the letters the database's LC_CTYPE knows,
  none of Cyrillic under `C`. A change to the rules is a migration that replaces the functions, then
  `ALTER TABLE spot ALTER COLUMN search_text SET EXPRESSION AS (search_words(title))` to recompute every row (a table
  rewrite fires no trigger, so versions stay put).
- **Ranking:** 1, every query word starts a word of the name or its city's name; 2, every word is inside the name;
  3, a word of 5–7 letters with one wrong letter or of 8+ with two (Levenshtein from `fuzzystrmatch`, against a whole
  word or the start of one); then distance from the optional point (`ST_DistanceSphere`), name, id. One `ORDER BY`
  with `LIMIT`, so typo matches show only when exact ones don't fill `limit`.
- **Indexes:** the trigram GIN `spot_search_trgm` serves `like` and `<%`; typo candidates come from `<%` with
  `pg_trgm.word_similarity_threshold` set for the transaction just under the weakest match the rule allows
  (`typoThreshold`), and Levenshtein confirms them. `spot_city_idx` serves city matches. On 100,000 generated spots
  (a busy laptop) most queries took 30–200 ms; a one- or two-letter word has no trigram, so it scans (one letter:
  about 0.6 s).
- `pg_trgm`, `unaccent` and `fuzzystrmatch` are on PlanetScale's list of extensions that need no superuser or restart.

## Paging

- **Lists that can grow without bound page by keyset** (`src/lib/paging.ts`), never OFFSET or COUNT. Paged now:
  `GET /v1/collections/{collectionId}/spots` (newest added first, 200 a page, at most 500). `GET
  /v1/collections/{collectionId}` carries the first page in `spots` and its `nextCursor`. The sync keeps its own integer
  version cursor (`hasMore`, tombstones, `resetRequired`: the app depends on them).
- **The contract:** query `cursor` (opaque, from the previous page) and `limit`; the answer is `pageOf(item, "<Name>Page")`,
  `{ items, nextCursor }`, `nextCursor` null on the last page. A cursor is base64url JSON of the last row's sort key,
  decoded by the list's key schema in the query (`pageQuery`), so a malformed one is a 422 like any bad query.
- **Adding one:** pick a sort key that is unique (end it with the id) and sorts one way, add a composite index on it in
  the same order, then `pageQuery({ key, defaultLimit, maxLimit })` in the route and in the service
  `.where(after(columns, cursor, order)).orderBy(...the same columns...).limit(limit + 1)` and
  `keysetPage(rows, limit, keyOf)`. A timestamp in a key is read as text (`::text`): a JS Date stops at milliseconds
  and the next page would skip or repeat rows.

## Contributions

- **Ids come from the app's outbox.** `PUT /v1/photos/{id}` and `PUT /v1/submissions/{id}` are idempotent: a
  retry lands on the same row. Photo uploads are immutable once stored. A pending submission is replaced by a
  resend; a decided one is returned unchanged. Another account's id is `forbidden`.
- **Unused uploads go after a week.** The daily housekeeping cron (`sweep`, 03:30 UTC, `src/services/housekeeping.ts`)
  deletes uploads older than 7 days that nothing uses (`isUnusedUpload`: no submission, collection photo or avatar),
  rows first and then their R2 objects once the connection is closed, up to 1,000 a day, and expired sessions.
- **A new spot may have no photo** (Ertem, 2026-10-30; 0–10): it shows its kind until an edit adds one.
- **Photos first, then the submission.** A submission referencing a photo the same account hasn't uploaded is a 422
  with `details.missingPhotos`.
- **Metadata never reaches storage.** `cleanJpeg()` (`src/lib/jpeg.ts`) keeps only what decodes the image (an allowlist:
  tables, frame, JFIF, ICC, Adobe), walks every scan, and cuts everything after the end marker (appended gain maps
  carry their own Exif). It's lossless and measures the size from the frame header, capped at 8192 px per side. Apple's encoder always writes Exif, so the server
  strips rather than refuses. R2 keys are random (`photos/<uuid>.jpg`) because they appear in responses.
- **Photo credit**: `credit` null means the uploader took it, and the API shows the uploader's name. Otherwise it's
  the named photographer, and `has_permission` must be true (CHECK constraint on `spot_photo` and
  `submission_photo`).
- **Requests are counted by who makes them** (`src/middleware/rate-limit.ts`; Cloudflare advises keys for a user, not
  an IP, which many people share): a signed-in request spends its account's `API_LIMITER` budget once `requireUser`
  knows it (`authedRoute`); a public operation spends its address's (`publicRoute`). Every request also passes a per-address
  flood guard (`ADDRESS_LIMITER`) before any database work, set above what riders behind one address would reach
  together, so made-up tokens can't hammer the session lookup.
- **Every write is limited per account and family** (`limitWrites(family)`, keyed `<family>:<userId>`; the family names its binding),
  so one kind of write never spends another's budget: tapping through votes can't stall the outbox. Route middleware
  goes after the config: `authedRoute(config, ...middleware)`. Over a limit is a 429 `rate_limited` with
  `Retry-After` (the window). A new write route picks a family; a new family needs no new binding unless its budget
  differs.

  | Family | Routes | Binding (namespace) | Budget |
  |---|---|---|---|
  | (per address) | everything under `/v1`, before anything else | `ADDRESS_LIMITER` (1005) | 3,000/min per IP or IPv6 /64 |
  | (per account, or address without a token) | everything under `/v1` | `API_LIMITER` (1001) | 600/min |
  | (per address) | `POST /v1/auth/apple` | `AUTH_LIMITER` (1002) | 20/min |
  | `contributions` | submissions, spot edits, photo and clip uploads, videos | `WRITE_LIMITER` (1003) | 60/min (a 10-photo spot is 11) |
  | `votes` | `PUT /v1/spots/{id}/vote` | `WRITE_LIMITER` | 60/min |
  | `collections` | save/delete a collection, add/remove spots, change a role, remove a member, cancel an invite, answer an invitation or a request | `WRITE_LIMITER` | 60/min |
  | `review` | approve/reject/undo spots, edits and videos; take a spot down or restore it | `WRITE_LIMITER` | 60/min |
  | `profile` | profile, block, unblock | `WRITE_LIMITER` | 60/min |
  | `outreach` | invite to a collection (@username or email), ask to join one, report | `OUTREACH_LIMITER` (1004) | 10/min |
- **Accounts can be deleted; contributions stay.** `submitted_by` and `uploaded_by` become null, and the photos
  stay with their submissions. Videos stay too, without attribution.

## Review

- **Who reviews where** (`reviewerRole()`, `src/services/review.ts`): curators decide everything in their cities
  (`city_editor`, granted by `grant-editor`, counted only while the account's role is `editor`); admins everywhere, including submissions outside every city. A curator decides an
  edit only when they curate both the spot's city and the one the edit puts it in (`reviewerRole`'s `fromCityId`), so
  an edit moving a spot between cities is for admins or a curator of both, and isn't in anyone else's queue. **Code owners** (Ertem, 2026-10-18): anyone decides the
  changes others suggest to a spot they added (`spot.created_by`): edits, the photos they bring, and videos, as
  `reviewAs: "owner"` in their queue. Owners don't rate (403) and may move their own pin anywhere. Your own change to
  your own spot goes to curators. So `/v1/review/*` needs only a signed-in account; `rateSpot` still needs `editor`.
  Every decision event records `details.as` (`curator` or `owner`).
- **Who hears about a pending change, and when** (`src/services/notifications.ts`; curators and admins can act at any
  time, this is only the pings): a change to someone's spot asks the owner at once (`spot-changes`), the city's
  curators after 3 days and admins after 7 (`review-queue`). A new spot asks the city's curators at once and admins
  after 7 days. "The city's curators" are those who could decide it (`curatorCities`): for an edit moving a spot, curators
  of both cities. A stage with nobody in it passes to the next at once (a city without curators: admins at once). Banned accounts are in no stage. The
  daily cron (`reviewEscalations`, 09:00 UTC, `src/schedules.ts`) walks the last 30 days' pending changes; a stage
  already sent is the same idempotency key, which BuzzKit replays without sending.
- **Decisions are rows plus an audit event** (`review_event`: approve with the edits, reject with the reason, undo),
  written in the same transaction as the decision while the submission row is locked (`FOR UPDATE`). A CHECK
  constraint keeps the decision consistent: pending has no `reviewed_at`; approved has a `spot_id`; rejected has a reason.
- **Approve** creates the spot (`uuidv7()` ids, Postgres 18) and copies the chosen photos into `spot_photo`.
  Repeating your own approval, rejection or undo returns it unchanged; deciding a decided submission is `conflict`
  (409). Approve and reject carry the `updatedAt` the reviewer saw: a resend since then is a 409, so nobody
  publishes content they never looked at.
- **Undo:** the reviewer, within ten minutes, or an admin, any time. Undoing an approval tombstones the spot; a new
  approval brings back the same spot id, so apps update the same pin.

## Spot edits

- **An admin's edit applies at once** (Ertem, 2026-10-19): the route approves it as its author right after saving (`approveSubmission`), so it's recorded and undoable like any approval and never queued or announced; if that approval fails it stays a pending suggestion. A resend of a decided edit returns the decision, even though the spot may already say what it asked for.
- **A suggested edit is a submission of kind `edit_spot`**. `PUT /v1/spot-edits/{id}` (`saveSpotEdit`, `src/services/spot-edits.ts`) follows the submission id rules (outbox id, a pending edit replaced, a decided one returned unchanged, photos first). Only real changes count: values equal to the spot's are dropped (obstacles compare as a set), nothing left is a 422, and a private, removed or unknown spot is a 404. The row holds the spot as the edit proposes it, `spot_id` is the spot it changes and `changed_fields` names what it changes (`submission_edit_shape` CHECK: a new spot changes nothing, an edit changes something).
- **Photos** (Ertem, 2026-10-30): an edit carries the spot's whole photo list as `photoEdit` (`order`: the spot's photos it keeps and its new uploads, the cover first; `base`: the list its editor showed, and `order` names only those and its uploads), so it reorders, removes and adds. Its `submission_photo` rows are new uploads (`photo_id`) or the spot's photos it keeps (`spot_photo_id`, no foreign key: a kept photo that's gone is skipped on read, and comes back if an undo restores it); `base_photo_ids` stores the base, and `photos` is in `changed_fields` only when approving it now would change the spot's photos. An edit without `photoEdit` (1.0.1) keeps the old shape: only the photos it adds, `base_photo_ids` null, and approval appends them.
- **Review:** the card carries `current` (the spot as it is now, with `removedPhotoCount`: the base's photos still on the spot that the edit leaves out) instead of nearby duplicates; `SubmissionPhoto.existing` marks the spot's own photos. Approve (`applyEdit`) writes only the changed fields, with the curator's adjustments winning, and makes the spot's photos the edit's list (`mergePhotoOrder`, `src/lib/photo-order.ts`, then `setPhotos`: new ones with uploader credit as usual): the photos it kept in its own order only if it reordered them (otherwise as the spot has them then, so a cover chosen since stays), none that are gone, then any the spot gained since the base; it moves the version. A whole-list photo change (`base_photo_ids` set, `photos` changed) is approved only with `wholePhotoList: true`, else 422 "Update OpenSkateMap to review changes to a spot's photos": 1.0.1 shows reviewers (curators and spot owners) its photos as additions, so they'd approve removals they never saw. An admin's own edit sends it. The approve event records what it replaced and the photos before (whole rows) and after. Undo (`revertEdit`) puts back each field the edit changed unless something changed it since, and the old photos (removed ones under their ids, unattributed if the uploader's account is gone, in the old order) while the spot's photos are still what the approval left. An approved edit counts in the editor's stats like any approved submission; "added by" stays with the spot's creator.

## Videos

- **Links, not files.** `spot_video` holds a YouTube video or an Instagram post/reel of a spot as provider + id
  + one normalised URL (`parseVideoLink()`, `src/lib/video-links.ts`: every pasted form of a clip gives the same
  value; other sites, channels and profiles are refused with 422). A new YouTube video must still play:
  `youtubeAvailability()` asks YouTube's keyless oEmbed (400/401/403/404 → 422 "private or no longer on YouTube";
  a timeout or 5xx lets it through for curators; a retry of a stored row isn't asked again). That is the only
  call to a platform: the YouTube thumbnail is `i.ytimg.com/vi/<id>/hqdefault.jpg`, and Instagram has neither a
  keyless check nor a thumbnail. e2e answers oEmbed with a stand-in `fetch`.
- **Curated like spots.** `PUT /v1/spots/{spotId}/videos/{videoId}` is the submission: the id is the app's outbox
  id (a retry lands on the same row, a pending one is replaced, a decided one returned unchanged, another account's
  is 403). The same clip can wait or show once per spot (partial unique index; a rejected one may be sent again),
  so a second copy is a 409. The review queue lists pending videos of spots in the reviewer's cities under
  `videos`; `/v1/review/videos/{id}/approve|reject|undo` decide them with the same rules as submissions
  (`seenUpdatedAt`, idempotent repeats, ten-minute undo, admins any time) and the same audit log (`review_event`
  has exactly one of `submission_id`, `video_id` and `spot_id`, the last for takedowns and restores). An admin's undo is how a shown video comes down.
- **Approved videos come with the spot's details** (`GET /v1/spots?ids=`), never in the sync index. A video
  appearing or leaving touches its spot (trigger, migration 0012), so the spot gets a new version and apps fetch
  its details again. Who added a video is hidden from a viewer who blocked them; the video stays.
- **Reports** accept `targetKind: "video"`.

## Clips

- **A clip plays in place of a photo**, looped, muted where it sits on a page and with its sound full screen; the photo stays its poster, so anything that shows only photos still works. `PUT /v1/clips/{clipId}` (`saveClip`, `src/services/clips.ts`) takes `video/mp4` up to 15 MB under the photo upload's id rules (outbox id, immutable, another account's is 403) at a random key (`clips/<uuid>.mp4`). A draft's photo names it as `clipId`, each clip once per draft, uploaded first (422 with `details.missingClips`).
- **Metadata never reaches storage here either.** `cleanMp4()` (`src/lib/mp4.ts`) takes exactly one H.264 track (`avc1`/`avc3`) and at most one AAC sound track (`mp4a`), of at most 16 s (`CLIP_MAX_DURATION_MS`, also `clip_upload`'s CHECK) and 1920 px a side (the track header's size, turned by its matrix), with `moov` before `mdat` (faststart), unfragmented. It rebuilds the file as `ftyp`, `moov` (`mvhd`, and each track's `tkhd`, `edts`, `tref`, `mdia`), `mdat`, zeroes recording times and moves every chunk offset to match. Any other track (and a second sound) is refused, never dropped: its samples would stay in `mdat`, and timed metadata can carry locations.
- **Served straight from R2** at `images.openskatemap.app/<key>`: a faststart MP4 plays as it loads, so no Images transformations (nothing counts against the cap), Stream or HLS.
- **Carried through review like photos.** Approval copies a new upload's `submission_photo.clip_id` into `spot_photo.clip_id`; an edit's kept photos have no clip of their own, so the spot photo keeps whatever it has. The approve event's photos before carry `clipId`, so undo restores it (dropped if the clip was swept since).
- **Details only**: `SpotPhoto.clip` and `SubmissionPhoto.clip` (`SpotPhotoClip`), left out when there is none. The sync index, share card and collections snapshot carry only the cover.
- **Unused clips go after a week** like photos (`isUnusedClip`: no submission's or spot's photo plays it), sharing housekeeping's 1,000 a day after photos, and with an account's other unused uploads when it's deleted.

## Votes

- **One vote per rider and spot** (`spot_vote`, primary key `(spot_id, user_id)`, `value` 1 or -1 by CHECK). The
  rating is how spots will be recommended. `PUT /v1/spots/{spotId}/vote` with `{ value: 1 | -1 | 0 }` sets,
  replaces or (0) clears it and answers `{ up, down, mine }`; the same vote again changes nothing. Published public
  spots only (404 otherwise), on their own `votes` budget (60/min per account).
- **Totals come with the spot's details** (`votes: { up, down, mine }` on `GET /v1/spots?ids=`, `mine` the
  viewer's own), never in the sync index. A vote never touches the spot row: it would move the version, the sync
  cursor, and every app would refetch. Apps refresh details on their own freshness clock instead.
- **The Spot Score** ranks spots (`GET /v1/spot-scores`: every published public spot, best first, `{ spotId, up, down,
  score }`, cached privately for a minute; the same for everyone, so each data center keeps one copy for that minute in the Cache API, `sharedAnswer`). `score` (0…1; ×100 is the index people see) is a weighted sum of votes
  shrunk toward a prior, saves, media and activity, times a condition factor. One query computes it
  into the materialized view `spot_score` (`packages/db/src/schema/spot-score.ts`, weights in `SPOT_SCORE`); the API's cron refreshes it every 10
  minutes (`refresh_spot_score()`, a `SECURITY DEFINER` function that refreshes it concurrently as its owner; the app role's name differs per environment), and the endpoint only reads it.
  Changing the query is `bun run db:generate`, which recreates the view: add its unique index and the `GRANT MAINTAIN`
  to that migration again (as in 0024), or the refresh fails. One response holds every public spot, a `shortcut:` to
  become a delta feed or per city.
- **No curators' rating** (dropped 2026-10-20, Ertem; migration 0028 removed `spot_curation` and its `rate` events):
  curators shape the map through review and edits, and its weight went to the score's other terms.
- **Votes are personal data**: they cascade away with the account, and nobody else sees who voted, only totals.
  A removed spot keeps its rows harmlessly; details never return it.

## Collections and private spots

- **Collections**: a rider's set of spots under their own id (`PUT /v1/collections/{id}`, idempotent). Changing
  someone else's is 403 when you can open it and 404 when you can't, so a private collection's id never confirms
  it exists. `private` (the default) is seen by the owner and its people; `public` by anyone
  signed in with the link, and listed on the owner's profile (`GET /v1/users/{id}/collections`). Someone the owner
  blocked gets `not_found`, as for profiles.
- **Favorites** (Ertem, 2026-10-18): every account has exactly one collection of `kind: "favorites"` (partial unique
  index), made by `favoritesOf()` with the account's first snapshot (amber, star pattern), listed first. It keeps its
  name (422) and can't be deleted (403); everything else works as for any collection. `PUT`/`DELETE
  /v1/me/favorites/{spotId}` star and unstar without the app knowing its id.
- **A collection's look** (`appearance`, Ertem 2026-10-18: a profile-style header): `color` (16:
  eight solid, eight two-tone), an optional `pattern` (an icon id the apps map to a symbol) and an optional `photo`
  (one the editor uploaded, as an avatar; account deletion keeps a photo a collection uses). `color` is always
  answered: unset, it's `automaticColor(id)`, the same for everyone. A draft's `appearance` replaces the whole look;
  leaving it out keeps it, so a rename never resets it. Editors change it. The iOS app sends only the photo (Ertem, 2026-10-19: no colour or pattern pickers), so its
  collections keep the automatic colour and no pattern; the fields stay for older builds.
- **Roles** (Ertem, 2026-10-18; `collection_member.role`, checked by `standing()` in `src/services/collections.ts`):
  **viewer** sees and shares it (the link) and sees who's in it; **editor** also changes its name, description and
  spots (and puts their own private spots in it); **admin** also invites, answers requests, changes roles, takes
  people off, changes the visibility and deletes it. The owner is above all three and is never a member row.
- **Invitations both ways** (Ertem, 2026-10-18): an invite (by the owner or an admin, with a role) always waits for
  the person to accept or decline (`…/invitation/accept|decline`); the snapshot lists yours under `invitations`.
  - By @username: the invite names them at once (usernames are public). An unknown username, or one whose owner blocked you, is 404.
  - By email: answered the same whether or not anyone has that email, so it never reveals who is registered. It's matched by the SHA-256 of the trimmed, lowercased email and becomes that account's invitation (`user_id` filled) when it calls `GET /v1/me/collections`. The access list keeps showing only the typed email, never the account it reached. Declining it, or its reaching someone already in, sets `declined_at` instead of deleting it: gone for them, still pending to the inviter, as for an address nobody uses. Only accepting changes what the inviter sees.
  - Invitations from someone you blocked (the owner or the inviter) aren't listed.
  - **Asking to join**: anyone with a link can ask (`POST …/requests`), answered the same whether the collection exists or not (and for someone the owner blocked); the owner and admins see `requests` in the access list and let them in with a role or turn them down (unannounced). Inviting someone who asked lets them in at once. The snapshot's `requestedIds` are your open requests.
  - Limits: 200 members and 100 pending invites per collection, checked under the collection's row lock. Inviting and asking count on the `outreach` budget (10/min). A member can leave (`DELETE …/members/{self}`).
- **Private spots** (`spot.visibility = 'private'`): made by `PUT /v1/submissions/{id}` with `collectionId` (a
  private collection the submitter edits: owner, admin or editor). It's published at once into that collection, never queued for review,
  and recorded as approved by its own submitter (`review_event.details.private`). It is never reviewed: no queue lists it, approve and reject are 403, and an admin's undo is a takedown (the spot is removed, the submission stays decided). Private is one SQL rule, `isPrivateSubmission` (`src/services/submissions.ts`), which reads the spot's `visibility` too, because deleting the collection clears `collection_id`. They don't count in profile stats.
- **Who sees a private spot** is one SQL rule, `canSeeSpot()` (`src/services/collections.ts`): its creator, or
  anyone who can open a collection holding it. That includes a public one, so making a collection public shows
  its private spots to anyone with the link; the app warns first.
- **Never public**: `GET /v1/sync/spots`, nearby, the share card, votes and videos (404) take public spots only;
  `GET /v1/spots?ids=` answers private ones only to viewers who can see them, with `visibility` on every detail.
  Private spots reach apps through `GET /v1/me/collections`, a snapshot of the viewer's collections plus every private spot they made or were given. A private spot missing from it is one the app must drop.
- **Only its maker puts a private spot in a collection** (and only one they edit), so a member of one group can't carry someone else's private spot into another.
- **Links**: `openskatemap.app/collections/<id>` is an app link (the AASA component); in a browser it's a generic
  page that names nothing (`collection.html`).

## People

- **Profiles** (`profile`, one row per account, created on first edit): username, bio, avatar (your own upload), six handles normalised on the way in
  (leading @ dropped, per-network rules).
- **Usernames** (Ertem, 2026-10-19): 5 to 24 English letters, digits or underscores (`profile_username_format`), shown in the case they were
  typed; uniqueness and @username lookups ignore case (`profile_username_lower_unique`). `isAllowedUsername` (`src/lib/usernames.ts`) refuses
  slurs and swearing (obscenity's English set, with its leetspeak and separator variants), our own names and role words, and companies' names
  (anywhere in the name, or as a whole word for everyday words like "palace"). Taken and refused are both `conflict`, "isn't available":
  the app shows one message. Add a word there when a report shows one got through. The display name stays on Better Auth's `user.name`. Emptying a field
  is `clear: [...]`, never `null`: the generated Swift client can't send an explicit null.
- **Public profiles never include an email.** Stats: submissions, approvals, cities with an approved spot.
- **Blocks** (`user_block`): the blocker no longer sees the blocked person's name on spots (added by, photo
  credit), and the blocked person gets `not_found` for the blocker's profile.
- **Deleting an account** (`deleteAccount`) cascades its votes away, and also deletes its unused uploads (the avatar, photos and clips never submitted),
  both rows and R2 objects. Submitted photos stay without attribution.
- **Reports** (`report`, App Store guideline 1.2) go to admins; the target must exist. Admins work them in the
  database for now.

## Push notifications

- **BuzzKit, self-hosted**: API `push-api.openskatemap.app`, dashboard `push.openskatemap.app`, deployed from
  [BuzzKit](https://github.com/buzzkit-dev/buzzkit)'s code plus our Wrangler config (it uses Wrangler, as upstream does) onto
  this Cloudflare account, its own `buzzkit` database and role on our PlanetScale cluster, and a Tinybird workspace.
  Sign-up is closed (a WAF rule on push-api). Its agent skill is `.agents/skills/buzzkit`.
- **The app owns the subscriber.** It identifies with our user id and `Me.pushIdentity` (HMAC of the id under the
  tenant's identity secret, `signPushIdentity`), sets the attributes (name, role, `cityId` = the city its map was last
  in) and asks for permission. The Worker never identifies: BuzzKit's server-side identify replaces attributes
  wholesale and would wipe the app's.
- **The Worker only sends** (`src/lib/buzzkit.ts` over BuzzKit's REST API; its npm SDK isn't published) and deletes
  the subscriber with the account. What each notice says and who gets it is `src/services/notifications.ts`; routes
  call `notifyAfter(c, compose)`, which composes on the request's connection and sends in `waitUntil`, so a notice
  never fails or slows a request. Every send names a topic and a business-event idempotency key.

  | Topic | When | To |
  |---|---|---|
  | `review-results` | a curator or the spot's owner approves or rejects a new spot, an edit or a video | the submitter (never for private spots) |
  | `spot-changes` | someone suggests an edit to, or adds a video of, a spot you added | the spot's owner |
  | `review-queue` | a pending submission or video arrives (first time only), or is still waiting (daily cron) | the city's editors, then admins (see Review); never the sender or the owner |
  | `collection-invites` | an invite by @username; a request to join; a request let in | the invitee; the owner and admins; the person let in (email invites tell nobody until they open the app) |
  | `new-spots` | Sundays 17:00 UTC (cron, `scheduled` in `src/index.ts`) | `where attributes.cityId` = each city with new public spots that week |

  A new topic is created in BuzzKit once (`POST /v1/topics` with the workspace key) before the code that sends it ships.
- Taps open universal links (spots, collections) or the app's named actions `open_contribute` and
  `open_review_queue`. Without `BUZZKIT_API_KEY` and `BUZZKIT_IDENTITY_SECRET` (local dev, tests) nothing is sent
  and `pushIdentity` is null.

## Analytics (PostHog)

- **One person, one id.** Everything is keyed by the account id: the app identifies with it after sign-in and resets
  on sign-out; the Worker sends it as `distinct_id`. No names, emails or free text in any event.
- **Who sends what.** The app sends screens (`$screen`, named by view controller class), app open and close, and
  intent the server never sees: how a spot was opened, directions, share, filters, search picks. The Worker sends
  the outcomes only it knows for sure, the typed catalog `ServerEvents` in `src/lib/posthog.ts` (submissions, edits,
  videos, review decisions, votes, takedowns and restores, collection shares, reports), with `track(c, event, properties,
  once?)` in `waitUntil`, so it never slows or fails a request. `once` names the business event (a submission id, a
  decision's id and `updatedAt`) and becomes a deterministic event `uuid`, which PostHog deduplicates, so the
  outbox's retries count once. A new event is a new `ServerEvents` entry first.
- **Opt-out.** Profile → Share Analytics off stops the app's SDK, and the app sends `DNT: 1` on every signed-in
  request, which `track` honours: nothing is sent about that person from either side.
- **Where people are.** PostHog's GeoIP transformation finds the country, region and city from the IP: the app's own
  connection, and for the Worker's events `$ip` from `CF-Connecting-IP` (`located`). The project discards the IP itself
  ("Discard client IP data"). No event carries a device's location.
- **Deleting an account** deletes its PostHog person and events (`deletePerson`: `persons/bulk_delete` with
  `delete_events`), next to the BuzzKit subscriber.
- **Env:** `POSTHOG_PROJECT_TOKEN` (the public `phc_` token), `POSTHOG_PROJECT_ID`, and `POSTHOG_PERSONAL_API_KEY`
  (a `phx_` key with only `person:write`, a secret). Without them nothing is sent or deleted (local dev, tests).
  Set (2026-10-15): project **OpenSkateMap** (id 666695, its own organization, US cloud) with "Discard client IP
  data" on; the token and id are texts in `cloudflare.config.ts`, the key a Worker secret set once with `cf workers
  secrets update`.
- PostHog's agent skill `posthog-best-practices` is in `.agents/skills` (`posthog-cli api skill install <id>`).

## Photo variants and the transformations cap

Apps load photos as sized variants from `images.openskatemap.app/cdn-cgi/image/...` (Image Transformations on the
R2 bucket's domain). The Images Free plan includes 5,000 unique transformations a month (each photo at each width
counts once a month); past that, new variants fail with error 9422 while variants already cached keep loading.

- **Alert:** the built-in "Image Transformation Notifications" policy (on, emails the maintainers' alert inbox) fires when
  the month's 5,000 are used up. Cloudflare has no early-warning threshold for it: Custom Alerts' only image dataset
  (`states.imageResizingRequests1m`) counts requests, not unique transformations, so no custom alert either (checked
  2026-10-12).
- **Usage now:** GraphQL `imagesTransformationsAdaptiveGroups` (account) gives daily counts.
- **When the email arrives, in order:** (1) request one width per `PhotoSize` instead of one per screen scale
  (`PhotoURLBuilder`, iOS ImageKit): halves the count, one line; (2) subscribe to Images Paid ($0.50 per 1,000 past
  the 5,000; the dashboard's Images → Plans), so nothing fails while (1) ships; (3) only if the bill matters, upload
  fixed sizes from the phone and serve them straight from R2, skipping transformations (API, schema and site
  changes, plus a backfill).

## Tooling notes

- The API is managed with the `cf` CLI (config in `apps/api/cloudflare.config.ts`). The website uses Wrangler (`apps/web/wrangler.jsonc`), as `cf` was too rough there.
- TypeScript is pinned to 6.0: typescript-eslint does not support TypeScript 7 yet.
- bun refuses packages younger than 7 days (global supply-chain guard); ranges resolve to the newest allowed release,
  and the one beta (`@cloudflare/vite-plugin` v2, required by the API's `cf dev`/`cf build`) is pinned exactly.
